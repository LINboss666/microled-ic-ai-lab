# 启动流水逐槽时间线（T2B-C）

**基线** `b02f824` ｜ **本轮** `T2B-C` ｜ 复位后第一帧的 slot 0 / 1 / 2 / 3 逐拍
**这份文件的用途**：解释"两级预充为什么不丢帧首两列"，以及 T2B-BR 那个 7,680 ns 违规窗口是从哪一拍漏出来的。

---

## 1. 一个槽里同时活着的四列

| 标签 | 含义 | 何时更新 |
|---|---|---|
| `rx` = s | 本槽正在接收的输入列 | 每槽 cycle 0（`COL_SYNC+DE+byte0` 同沿）|
| `fwd` = s | 本槽 cycle 831 起向 Data 转发的那一列 | `load_done`（下一槽 cycle 623）记录 |
| `disp` = s | **Data 显示 bank 里现有的那一列** | 本槽 cycle 827（`latch_evt`）从 `fwd` 取 |
| `lit` = s | 本槽 PWM 窗口（cycle 0..767）实际点亮的那一列 | 上一槽 cycle 827 的 `disp` |

**关键事实**：`disp` 在 827 更新，LATCH 脉冲在 828..831 发出。Data 模型在 828 的上升沿把输入缓冲切进显示 bank。
所以 **827 写入的 `disp` 和 828 完成的切换是同一列的同一件事**，不是"提前一个槽的预测"。
（这是 T2B-BR 之前读错的地方：当时以为 `disp` 比 Data 的提交早一个槽。）

---

## 2. 复位后第一帧（`latch_cnt` = 已发出的 LATCH 个数）

| 槽 | 区间（cycle） | `rx` | `fwd` | `disp`(827 起) | `latch_cnt` | BLANK | Data 显示 bank | 说明 |
|---|---|---|---|---|---|---|---|---|
| 0 | 0..767 | 列 0 | — | — | 0 | **1** | 空（reset） | 无许可：`disp_ok=0` |
| 0 | 827 | 列 0 | — | 无效（`fw=0`） | 0 | 1 | 空 | 首个窗口还没关闭 |
| 0 | 828..831 | 列 0 | — | 无效 | **1** | 1 | 空 | **预充 LATCH #1**：初始化 Data 装载计数 |
| 0 | 832..1598 | 列 0（转发） | 列 0 | 无效 | 1 | 1 | 空 | 384 B ×2 口写入 Data 输入缓冲 |
| 1 | 0..767 | 列 1 | 列 0 | 无效 | 1 | **1** | 空 | 仍无许可（`disp` 无效） |
| 1 | 623 | 列 1 | 列 0 完成 | — | 1 | 1 | 空 | `load_done` → `fw`=列 0、valid |
| 1 | 827 | 列 1 | 列 0 | **列 0（valid）** | 1 | 1 | 空 | 标签就位，但预充只有 1 级 |
| 1 | 828..831 | 列 1 | 列 0 | 列 0 | **2** | 1 | **列 0** | **预充 LATCH #2**：切进显示银行 |
| 1 | 880 | 列 1 | 列 0 | 列 0 | 2 | 1 | 列 0 | 首个 SCAN_STB（列 0），`COL_ID=0` |
| 2 | 0..767 | 列 2 | 列 1 | 列 0 | 2 | **0** | 列 0 | **首个发光窗口：显示列 0** |
| 2 | 827 | 列 2 | 列 1 | 列 1 | 2 | 0 | 列 0 | 标签前进到列 1 |
| 2 | 828 | 列 2 | 列 1 | 列 1 | 3 | 0 | 列 1 | LATCH：切进列 1 |
| 2 | 880 | 列 2 | 列 1 | 列 1 | 3 | 1 | 列 1 | SCAN_STB（列 1） |
| 3 | 0..767 | 列 3 | 列 2 | 列 1 | 3 | 0 | 列 1 | 显示列 1 |
| 3 | 828 | 列 3 | 列 2 | 列 2 | 4 | 0 | 列 2 | …稳态 |

**结论**：列 0 在槽 2 的窗口被点亮，列 1 在槽 3 的窗口被点亮。**帧首两列都显示了，只是整体延迟两个槽**——
这正是 V1.3 §9「显示帧边界相对输入延迟，但不丢失帧首两列」。

## 3. T2B-BR 的缺陷在哪一拍

修复前 `latch = latch_seq && safe && !flt && (!act || fw_ok)`：

* 槽 0 的 `fw_ok = 0`（还没有任何窗口关闭）→ **槽 0 的 LATCH 被吞掉**，`latch_cnt` 一直是 0，Data 从不 arm；
* 槽 1 才有第一个 LATCH（VCD 里 19,045 ns）→ 那次上升沿 `armed=0`，提交失败；
* 但 `disp` 在槽 1 的 827 就已经是"列 0 有效"（TCON 自己的预测），`disp_ok=1`；
* 于是**槽 2 的窗口（20,535..28,215 ns，7,680 ns）在 Data bank 仍然无效时被解除 BLANK**，
  Scan 也已选中列 0 —— 这就是复审从原始 VCD 抓到的违规；
* 首个真正有效的 bank 出现在 28,826 ns，装的是**列 1** —— 因为列 0 的 384 B 从没被捕获过。

**根因**：把"结构性时序信号"LATCH 当成了"有数据才发"的许可信号。
LATCH 是 Data 芯片预充流程的一部分，它必须在 BLANK 内无条件（对 safe 而言）发出。

---

## 4. 修复后的许可合同（一行写清）

```
display_permit = ACTIVE && (disp label valid && !poison) && (latch_cnt >= 2)
BLANK          = blank_seq || !safe || flt || !ACTIVE || (ACTIVE && !display_permit)
LATCH          = latch_seq && safe && !flt           （不受 permit 影响；预充在 BLANK 内进行）
PWM_START/SCAN_STB/PWM_TICK = 对应脉冲 && safe && !flt && ACTIVE && display_permit
```

三条门互相独立：**有没有合法帧**（ACTIVE）、**标签指的那一列是否有效**（disp）、
**Data 的预充是否走完**（`latch_cnt>=2`）。任何一条不成立，外部就看不到发光许可。

---

## 5. 这张表能证明什么、不能证明什么

**能**：列 0 / 列 1 的接收→转发→提交→选通→发光链条在槽 2 / 槽 3 完整闭合；预充两槽内 BLANK 恒高。

**不能**：
* `latch_cnt` 是 TCON 自己数的 LATCH 个数，不是 Data 的反馈（V1.3 没有这条物理线）。
  它与 Data 的实际提交是否一致，只能靠**独立 Data 模型**在仿真里核验——即 T2B TB 的 `P52`（BLANK 为低时两颗 Data bank 必须有效）。
* 真实 LED 是否亮，取决于驱动阵列电气模型（未实现）。
