# 错误状态可见性（STATUS_VISIBILITY）

日期：2026-11-19　针对复审 P1-A：「`mb_lost` / `mb_badlen` 仅内部观测，Host 经四线 SPI 读不到」

---

## 1. 现状核对（源码事实）

| 信号 | 位置 | 是否 SPI 可读 |
|---|---|---|
| `mb_lost` | `spi_frame` → `tcon_spi_top.mb_lost_o` | ❌ 只是模块输出脚，`tcon_spi_regs` 无此输入，无对应寄存器位 |
| `mb_badlen` | 同上 | ❌ 同上 |
| `wr_frames` / `wr_cap_cnt` / `wr_rej_cnt` | 同上 | ❌ 观测用，未映射 |
| `err_reg` | `tcon_spi_regs` → `fault_status[8]` | ✅ 读 0x0C 的 bit8 |
| `fault_status` / `int_status` / `status` | 寄存器 | ✅ 0x0C / 0x10 / 0x18 |

所以 `gates.txt` 里"`mb_lost` 是可读标志"的说法**不成立**，本轮更正并登记。

---

## 2. 为什么必须让 Host 能看到

| 事件 | 后果 | 如果不可见 |
|---|---|---|
| `mb_badlen` | 一笔 SPI 事务长度不是 48（47/49/截断），寄存器未被写入 | Host 以为写成功了，实际配置没生效 |
| `mb_lost` | 上一笔写还没被 core 消费，新帧到达被丢弃 | 静默丢配置，且发生时序违规（CS 高 < 100 ns）无从发现 |
| `wr_rej_cnt` | 写被规则拒绝（ERR_REG 已可见） | 已覆盖，无需新增 |

前两条都是**配置完整性**问题：芯片照常运行，但运行在 Host 不预期的配置上。这比报错更难查。

---

## 3. 三个候选落点

### 方案 A（推荐）：并入 `ERR_REG`（FAULT_STATUS[8]）

```
err_set |= mb_badlen_evt | mb_lost_evt
```

| 优点 | 缺点 |
|---|---|
| 复用已有位，**不加地址、不改寄存器表** | 分辨率低：Host 只知"有访问错误"，不知是长度错还是丢帧 |
| `ERR_REG` 已实现 W1C + 只读回读 | `ERR_REG` 不参与 `disp_fault`，**不会熄屏**（符合"配置错误 ≠ 显示故障"） |
| 与 V1.3「非法 SPI 格式置 ERR_REG」一致 | 需要把两个单比特事件送进 core 域（见 §4） |

副作用可控：一次 30 沿的短帧不会熄屏，只会置错误位，Host 读 0x0C 可见、写 0x0C 清掉。

### 方案 B：并入 `COMM_TO`（FAULT_STATUS[7]）

| 优点 | 缺点 |
|---|---|
| 语义上"通信故障"更贴近 | `COMM_TO` 属于**显示类**故障 → 一次坏帧就会熄屏，对调试期过于激进 |
| V1.3 已有该位 | 会把"Host 写错长度"和"链路断了"混为一谈 |

**不推荐**作为默认，但可作为"严格模式"的可选项（参数化）。

### 方案 C：新增只读诊断寄存器 `0x28 SPI_DIAG`

| 位 | 含义 |
|---|---|
| [0] | `mb_badlen`（曾有长度非 48 的事务） |
| [1] | `mb_lost`（曾有写帧被丢弃） |
| [2] | `wr_busy`（邮箱有未消费帧） |
| [15:8] | `wr_frames` 低 8 位（已发送帧计数，用于对账） |
| [23:16] | `wr_cap_cnt` 低 8 位（已捕获帧计数） |
| [31] | 计数器回绕（sticky） |

| 优点 | 缺点 |
|---|---|
| 分辨率最高，可对账 `frames_sent == frames_captured` | **0x28 不在 V1.3 寄存器表内**，属于规格扩展，需要独立批准 |
| 只读，不改变任何安全行为 | 增加一次地址译码与 32 位读通路 |

**建议**：先做 A（零规格变更），把 C 作为可选诊断提交规格评审；不要在未批准前占用 0x28。

---

## 4. 跨域送进 core 的最小做法（供方案 A）

`mb_lost` / `mb_badlen` 是 **CS_n 域的粘滞位**，不能直接当脉冲用。两种等价做法：

**做法 1（推荐，与现有 epoch 同构）**：把它们并进写帧 epoch 的载荷——
在 `spi_frame` 增加 `wr_flags[1:0] = {mb_lost, mb_badlen}`，随 `wr_frame` 一起保持，
core 在每个 `wr_cap_o` 上采样。因为只在 CS 上升沿更新、core 在 2FF 之后才读，天然满足
"稳定多位 + 单比特限定"的既有 CDC 形态。

**做法 2**：各自 2FF 同步成电平，core 检测上升沿置 `ERR_REG`。缺点是两个额外同步链，
且 `mb_badlen` 可能在同一个 48 沿帧内先置位（对 49 沿来说发生在 CS 之后），时序更绕。

无论哪种，**都只是"把已存在的粘滞位送进 core 域"**，不改变 `spi_frame` 的帧语义。

---

## 5. Host 侧建议的读法（写进驱动合同）

1. 每笔写事务后读回目标寄存器，比对期望值 —— 这是最强的完整性检查，不依赖新位；
2. 周期性读 `0x0C`：bit8=1 表示"至少发生过一次访问错误"（含坏帧长/丢帧，方案 A 落地后）；
3. 读 `0x10`：`INT_STATUS` 可让 Host 用中断而非轮询发现错误（`INT_EN` 只屏蔽通知，不改状态）；
4. 发现 bit8 后：**先修 SPI 时序**（保证 CS 高 ≥ 100 ns），再 W1C 清除，再重新下发配置。

---

## 6. 本轮不做的事

- **不改寄存器表**（0x28 需规格批准）；
- **不改 `spi_frame` 端口**（方案 A 的载荷扩展属下一阶段，需连同 patch 一起评审）；
- 因此**当前仍不能声称"通信异常具备完整软件诊断能力"**，只能在报告里写
  "`mb_lost` / `mb_badlen` 为内部观测，Host 暂不可读（P1-A，已登记）"。
