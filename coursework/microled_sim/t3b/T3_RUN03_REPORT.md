## 3. 复审预警的采样口径问题：确实存在，且能解释 col2

### 3.1 第一层（run02 的根因之一）：`din` 随 `sent` 在 posedge dclk 更新

DUT 在沿前采样，`data_model` 在沿后 1 ns 采样 → 两个模型恒定错开一个字节。
这解释了 run02 里 D14/D15 对列 1、列 2 的失败——**不能归因于新 RTL**。
修法：`win`/`sent`/槽波形全部改在 **negedge** 更新，给每个 DCLK 上升沿 5–10 ns 建立/保持。

### 3.2 第二层（run03 才暴露）：976/977 奇偶造成的相位漂移

修掉第一层后仍然 col2 挂。原因：**槽长是 976/977 交替（977 是奇数）**，
LATCH 下降沿（在 negedge clk 寄存）相对 negedge-dclk 网格每遇到一个 977 槽就漂 10 ns。
漂移后 LATCH 下降沿落在"arming posedge 之后"的相位里，`sent` 在 arming 之前就多走一步 →
**oracle 的字节流整体错位一字节**（DUT 因有 `din_valid` 门控不受影响）。

验证：递推槽长序列 slot0=976、slot1=**977**、slot2=976…
- col0（slot0 窗）：不漂 ✓ 与 oracle 一致
- col1（slot1 窗）：不漂 ✓ 与 oracle 一致
- col2（slot2 窗）：slot1 是奇数长 → **漂了** ✗ 与 oracle 错一字节

与 run03 的 PASS/FAIL 分布**逐列吻合**。

### 3.3 修法（已应用，未验证）

`win` 在 **LATCH 上升沿**检测时打开（远早于下降沿，任何相位都来得及）；
`sent` 只从 **arming posedge**（`latch_p && !latch`，即 DUT 真正吃 byte0 的那一拍）之后开始计数；
`din_valid = win && !latch && sent<win_nb`。这样两个相位下 arming 拍都满足 `din_valid=1` 且 `din=byte0`，
DUT 与 oracle 全窗逐字节一致。

## 4. D42 为什么挂（我自己的统计写错了，不是 RTL 问题）

`T3_WINDOW_CENSUS windows=9 min=81 max=385`：
- `min=81`：P6 复位把**还在传输中的窗口**强行关掉，快照把那半截窗算进去了；
- `windows=9` 而不是 13：窗口被"新 LATCH 下降沿到来时仍未关闭"的情况合并。

修法（已应用）：快照只在**正常关闭**（`sent` 计满）时进行，异常关闭（复位/被新窗顶掉）直接丢弃。
这是统计口径修正，不涉及任何判据。

384 字节/窗的功能性证据仍然成立：`col_valid=1` 要求 `wcnt==384`，
且 D19 的 384 路导通拍数逐路核对只有在显示 bank 精确等于 ramp 图案时才可能通过。
